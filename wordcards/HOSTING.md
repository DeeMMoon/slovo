# GitHub Pages + Supabase

## Подготовлено

- `.github/workflows/pages.yml` публикует `wordcards/dist` после проверок.
- `supabase/migrations/001_shared_cards.sql` создаёт общий словарь и личный прогресс с RLS.
- `supabase/seed.sql` добавляет стартовые карточки отдельно от схемы.
- `dist/cloud.js` использует официальный Supabase JavaScript SDK и почтовые аккаунты.
- Сохранение выполняется одной транзакцией через RPC. Конфликт редактирования отменяет всю операцию. При сетевой ошибке интерфейс сообщает, что сохранение не подтверждено, и предлагает обновить словарь.

## Перед публикацией

1. Подключить аккаунты GitHub и Supabase к Codex. Не передавать пароли, service_role и личные токены в чат.
2. Создать или выбрать бесплатный Supabase-проект. Использовать отдельный проект или проверить отсутствие конфликтующих таблиц `slovo_*`.
3. Применить миграцию `supabase/migrations/001_shared_cards.sql` один раз, затем выполнить `supabase/seed.sql`. При повторных изменениях добавлять новые миграции.
4. Проверить включённый вход по email/password и способ отправки регистрационных писем. В Supabase Auth настроить Site URL и разрешённые Redirect URLs на точный адрес Pages с путём репозитория и завершающим `/`. Для восстановления пароля используется этот же адрес.
5. Создать публичный репозиторий для бесплатного GitHub Pages. В репозитории должны находиться папка `wordcards` и корневая `.github`. Исключить резервные копии и секреты.
6. Публичные настройки Supabase уже записаны в `dist/config.js`. При необходимости их можно переопределить переменными GitHub Actions `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY`. Скрипт публикации проверяет конфигурацию и отклоняет secret/service_role ключи.
7. В Settings → Pages выбрать Source: GitHub Actions. Отправить исходники в `main`, дождаться успешной публикации и проверить выданный адрес.
8. На двух тестовых аккаунтах проверить: регистрация, вход, восстановление пароля, общая новая карточка, раздельные статусы, запрет редактирования чужой карточки и сохранение после смены устройства. Затем импортировать локальную резервную копию владельца через интерфейс сайта.

## Права доступа

Словарь доступен вошедшим пользователям. Добавлять слова могут все вошедшие пользователи, редактировать и удалять — только автор. Стартовые карточки с `owner_id = null` изменяются администратором базы. Удаление авторской карточки убирает её у всех и удаляет связанные статусы; интерфейс предупреждает об этом до подтверждения.

Прогресс привязан к `auth.uid()`. Email и пароли в таблицах словаря не хранятся; вход обслуживает Supabase Auth. Другой пользователь не может прочитать или изменить чужой прогресс даже прямым запросом к API.

Резервная копия из интерфейса содержит общий словарь и прогресс текущего пользователя. Для восстановления прогресса всех пользователей владелец отдельно экспортирует базу средствами Supabase CLI и хранит копию вне публичного репозитория.

## Текущий статус проверки

В Supabase создан проект `vwopbdmxlxswmididevm`, схема применена, загружено 18 стартовых карточек. Проверены RLS на обеих таблицах, запрет анонимной записи и 7 политик доступа. Транзакционный тест `tests/rls-smoke.sql` подтвердил общий словарь, приватность прогресса и запрет изменения чужих карточек; тестовые данные отменены через ROLLBACK. С этого момента применённую `001_shared_cards.sql` не изменять — дальнейшие изменения оформлять отдельными миграциями.

Репозиторий создан: https://github.com/DeeMMoon/slovo. Публикация GitHub Pages и регистрация реальных пользователей пока не завершены. Для почтового подтверждения регистрации и сброса пароля внешним пользователям необходимо настроить SMTP: стандартный SMTP Supabase доставляет письма только участникам организации.
